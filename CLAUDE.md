# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

`code-helper` — pip-installable Python CLI that generates and manages small bash wrapper scripts in `~/.local/bin`. Each wrapper (`deepseek`, `glm`, ...) points Claude Code at a different model backend by exporting `ANTHROPIC_*` env vars and execing `claude "$@"`. Not affiliated with Z.ai, Moon Bridge, or Codex — successor to the archived `zai-codex-helper` project, stripped down to just this one feature.

## Commands

```bash
pip install -e ".[dev]"        # editable install + dev tools
pytest -q                       # run tests
ruff check . && ruff format .   # lint + format (the project's only linter)
```

## Architecture

Three-layer split, much smaller than the archived predecessor:

- **`cli/parser.py`** — argparse tree (`list` / `add <name> [--model]` / `edit-token [<name>]` / `tui`, plus bare `code-helper` defaulting to `tui`). Handlers are thin shells: resolve `Paths.default()`, delegate to a service, let `CodeHelperError` propagate to `__main__.main()`.
- **`cli/menu.py`** — a hand-rolled arrow-key terminal menu (`select_from_menu`), stdlib-only (`termios`/`tty`/`select`, Unix-only) — consistent with "No Rich/Typer" below. Split into two layers: `_translate(first_byte, read_more)` is a PURE key-sequence parser (no TTY) that turns a byte plus an injectable non-blocking `read_more(timeout) -> str | None` peek into a key name — fully unit-tested in `tests/test_keys.py` without a real terminal; `_read_key_raw` is the thin `termios`/`tty` wrapper that owns the real TTY (via `os.read(fd, 1)`, never `stream.read(1)` — see note below) and feeds `_translate`. `select_from_menu` takes `read_key` as an injectable callable so tests never touch a real TTY. Menu items are `str` or `(value, label)` pairs — the label renders, the value is what callers compare against and what gets returned; a plain `str` is both, so every pre-existing call keeps working. Items are numbered `1`-`9` in the printed gutter by the menu itself (not the caller) — the same place that handles the `DIGIT_<n>` key — so the shown number and the number that selects it can never drift apart; a value passed in the `unnumbered` set (e.g. a trailing "← назад"/"quit" entry) gets `·` instead of a digit, so it never eats a shortcut a real item needs. An optional `hint` string renders below the list. Every printed row (heading, item, hint) is truncated to `shutil.get_terminal_size().columns` on a real TTY via `_fit` — **this is a correctness fix, not cosmetic**: a row longer than the terminal wraps into extra physical rows the in-place redraw's `frame_lines` counter (a count of logical rows) doesn't know about, and the menu visibly creeps down the screen on every keypress (this actually happened: the `add` wrapper-picker rows were 85-90 columns wide before this fix, wrapping on any 80-column terminal). Off a TTY nothing is truncated — there's no redraw to protect. The heading and hint each get one blank spacer line for visual separation from the list, folded into the SAME `print_fn` call as a leading/trailing `\n` (not a separate call) — so `frame_lines = len(pairs) + 2 + (2 if hint else 0)` (was `+1`/`+1` before spacers existed) is the one place that has to know about them; get it wrong and the redraw erases the wrong number of rows. Navigation: arrows or vim `j`/`k`, `Home`/`End`/`g`/`G`, `PageUp`/`PageDown`, digits `1`-`9` for direct selection. `MenuCancelled` carries `hard: bool` — `True` for Ctrl-C (immediate, unconditional exit), `False` for Esc/`q` (default "go back one level"); defaults to `True` so an un-inspected `except MenuCancelled` keeps the old "cancel = stop" behavior. **Ctrl-C in raw terminal mode never raises `KeyboardInterrupt`** (`ISIG` is off) — it arrives as the raw `\x03` byte and MUST be translated to its own `"HARD_CANCEL"` key, distinct from Esc/`q`'s `"CANCEL"`; folding them together silently turns every Ctrl-C into a soft "back" instead of "quit everything" (a real regression this project shipped and fixed — see `tests/test_keys.py::test_ctrl_c_is_a_distinct_hard_cancel`). `press_any_key(prompt)` is the public "block for one keypress" primitive (TTY-gated, no-op off a TTY) used by the TUI's post-command pause; it fully parses one key via the same layer, so an escape sequence isn't misread as several separate "any key" presses. The cursor is hidden for the duration of a menu (`\033[?25l`/`\033[?25h`), restored in a `finally` even on exception. On a real TTY the menu redraws *in place* each keypress (cursor-up + clear-to-end ANSI escapes), so navigation doesn't scroll an endless stack of menus; on a non-TTY (pipe/tests with injected `print_fn`) it falls back to reprinting each frame.
- **Reading a raw keypress: `os.read(fd, 1)`, not `stream.read(1)`.** `sys.stdin` is a buffered `TextIOWrapper` — a single `.read(1)` call is free to pull more than one byte off the fd into its own internal buffer before decoding and returning the first character. `select.select` only ever sees the fd itself, with no visibility into that internal buffer, so a byte the wrapper already buffered can never show up as "ready" again — `_read_more`'s `select` call then waits out its timeout for a byte that already arrived, and the *next* menu redraw's `read_key()` blocks forever on a `select` that will never fire. This was a real, hard-to-reproduce hang (only under a real PTY driving fast keypresses — the injected-`read_key` test suite can't see it at all) — `_read_key_raw` reads every byte straight off the fd via `os.read` instead, so `select` and the actual read never disagree about what's pending. Bytes are decoded **one at a time** with `errors="replace"`, so a multi-byte UTF-8 character (a Cyrillic letter, say) becomes several U+FFFD → `"OTHER"` keys — harmless for a menu that only acts on ASCII and ignores `"OTHER"`, but this reader is **not** reusable for text input without first accumulating continuation bytes into a whole character.
- **Peeking past a keypress needs pushback (`_pending_byte`).** `_translate` peeks one byte past Enter to detect the LF half of a CRLF. A peeked byte is already off the fd and cannot be un-read, so when it turns out *not* to be the pair byte — the user pressed Enter and then, within the window, another key — it must be parked in the module-level `_pending_byte` slot and drained by the *next* `_read_key_raw` call, which is why that slot is module-level rather than a local. Dropping it instead (the original "swallow whatever shows up" behavior) silently lost that keypress: "Enter then Down" typed quickly just didn't move. The peek uses `_PAIR_TIMEOUT` (~2 ms), not `_ESC_TIMEOUT` (50 ms) — a real CRLF pair arrives in one burst from the terminal driver, so the longer wait bought nothing and added 50 ms of latency to *every* Enter. One byte of pushback is enough: only the Enter branch pushes, at most one byte, and the next call drains it before it can read anything else. `_translate`'s `push_back` parameter defaults to a no-op discard so every caller that only wants key *names* (and every `_translate` unit test) is unaffected.
- **`cli/tui.py`** — a looping arrow-key menu wrapping the CLI 1-to-1 (issue #3's contract: CLI primary, TUI secondary, no new *behavior*). `run_tui` mutates the shared `argparse.Namespace` (`name`/`model`/`dry_run`/`debug`) and calls the *same* `_handle_list` / `_handle_add` / `_handle_edit_token` from `cli/parser.py` — it never touches `services/` directly, so TUI and CLI cannot diverge in behavior. The one read-only exception is `services/wrappers.py`'s `describe_all` (built on `is_installed`), called purely to label menu entries — `_handle_edit_token` in `parser.py` builds the exact same shape of labels over its own (secret-only) subset of `WRAPPERS`, so this one helper is what keeps the two wrapper-listing menus from drifting apart on either row layout or the `Paths`/`is_installed` wiring behind it. Labeling and screen order are presentation, not behavior, and are the TUI's job: every menu item shows a description, and `add`'s wrapper/settings sub-menus show install state / the current toggle value, none of which duplicates a service call or validation rule. Navigation is uniform: **Esc/`q`** goes back one level (a sub-menu returns to the main menu; the main menu exits) via `MenuCancelled.hard=False`, folded by the local `_pick` helper into the same `_BACK` sentinel value picking the visible "← назад" item returns — every call site checks the result ONE way; **Ctrl-C** (`hard=True`) is left to propagate as `MenuCancelled` and is caught once, at the very top of `run_tui`, so it exits the whole TUI immediately from any depth rather than being handled ad hoc at each call site. Every sub-menu also has a visible `← назад` entry, since the keyboard shortcuts aren't discoverable from the screen alone; it (and the main menu's `quit`) is passed to `select_from_menu`'s `unnumbered` set, and `_pick` derives the hint's digit range (`1-4`, not always `1-9`) from how many *other* items are on screen — see `_hint` — so the printed range can't drift from what the digits actually do. There is no `dry-run` menu toggle — `--dry-run` is a scripting/debugging flag, read from `args` but never mutated by the menu; `code-helper --dry-run` (or `tui`) still works. `debug` lives in a `settings` sub-menu instead of main-menu real estate. `add`'s model prompt is two menu picks (wrapper, then "keep default" vs "enter custom") rather than a bare `input()` — the common case never calls `input()` at all, and the default model is shown in the label. A `CodeHelperError` from `add`/`edit-token` is printed to stderr and the menu reappears (re-raised under `--debug`, mirroring `__main__.main`); a `KeyboardInterrupt` from a plain `input()` (the custom-model prompt) is also caught and treated as "back", never crashes the TUI. After a command runs, the screen clears and the menu re-renders at the top — but only after a keypress (`[нажмите любую клавишу, чтобы вернуться в меню]`), so the command's output stays readable instead of being wiped instantly; on a non-TTY the pause is a no-op so tests never block; a hard Ctrl-C mid-command skips the pause entirely (the user already asked to leave). Both `select_from_menu` and `input` are looked up at call time (not bound as function defaults) so tests can `monkeypatch.setattr` them — a `= input` default parameter would bind the builtin at def-time and silently ignore the patch. `_handle_edit_token`'s own wrapper picker (in `parser.py`) re-raises a hard `MenuCancelled` instead of swallowing it into `"cancelled"` + exit 0, specifically so a TUI caller can still tell "back" from "leave the whole TUI" apart even though that handler is shared with the plain CLI path.
- **`services/wrappers.py`** — the core. `WrapperSpec` (frozen dataclass) + the `WRAPPERS` registry (`deepseek`, `glm`, `glm-ollama`). `render_script` (pure), `install_wrapper` / `is_installed` / `list_wrappers`. `describe_wrapper` (one formatted `name / state / description` row) + `describe_all` (that row per spec, paired with its name, each state resolved through `is_installed`) are the single source of truth for every wrapper listing — `list_wrappers`, the TUI's `add` picker, and `edit-token`'s picker all render through `describe_all`, so none of them re-derives `script_for(...).exists()` inline; the helper shares the `Paths`/`is_installed` wiring, not just the column widths. Callers pass their own `installed_word`/`not_installed_word` (English for `list_wrappers`, Russian for the TUI) — only the format is shared. `install_wrapper` writes `~/.local/bin/<name>` unconditionally by name — no ownership marker, no "foreign file" guard; whatever was there before (helper-generated or hand-written) is replaced.
- **`services/secrets.py`** — resolves a wrapper's token: env var first, hidden `getpass` prompt otherwise. No persistent config file — the token lives only inside the generated script. **Not used by `edit-token`**: that command always prompts via `getpass` directly, because `resolve_token`'s env-var-wins behavior would otherwise silently ignore whatever the user types when the env var (e.g. `ZAI_API_KEY`) happens to already be set.
- **`services/paths.py`** — frozen `Paths` dataclass, one field (`bin_dir = ~/.local/bin`). `Paths.from_home(home)` is pure path arithmetic; `Paths.default()` wraps `Path.home()`.
- **`backends/_atomic.py`** — the only code that touches the filesystem. `atomic_write(path, data, mode)`: temp-sibling + fsync + `os.replace`, crash-safe.
- **`errors.py`** — `CodeHelperError` lives here (not in `__main__`) to avoid a class-identity split under `python -m`.

## Key Constraints

- **Every wrapper is DATA** (a `WrapperSpec` in `WRAPPERS`), never a hand-edited string — adding a new backend is a registry entry, not new logic.
- **Two wrapper shapes**, discriminated by `launch_command`: the **env-var shape** (`launch_command is None`, the original) exports `ANTHROPIC_*` and runs `claude "$@"`; the **command shape** (`launch_command` set, with a `{model}` placeholder) `exec`s a provider's own launcher (`ollama launch claude --model {model} -- "$@"`) and skips the `ANTHROPIC_*` exports — that launcher sets them itself. The `--` before `"$@"` is required: without it, the launcher's own flag parser consumes forwarded Claude flags (e.g. `-p`) instead of passing them through. `render_script` branches on `launch_command is not None`; the env-var path is unchanged.
- **The `auth` field** (`"literal"` vs `"secret"`) is what keeps this generic: a literal token (e.g. Ollama's local daemon accepts `"ollama"`) needs no prompt and gets mode `0o755`; a secret token is resolved interactively/from env and gets mode `0o700` (owner-only — the script carries it in plain text).
- **Shell-injection defense**: every value interpolated into a generated script — token, base URL, model names — goes through `_shell_single_quote` (POSIX `'` → `'"'"'`). This matters because `--model` makes the model name user-controlled input, not just a registry constant.
- **No ownership guard**: `install_wrapper` overwrites `~/.local/bin/<name>` unconditionally, by name only — there is no "remove" command and no protection against clobbering a pre-existing, non-code-helper-managed file. Validation is limited to the wrapper `name` itself (`get_spec` rejects unknown names before any prompt or write).
- **No Rich/Typer** — plain text, argparse (stdlib) only.
- **`--dry-run`** never writes any file — prints what would happen instead.
- **TUI is a mirror, not a second implementation**: every TUI menu item must dispatch into an existing `_handle_*` with the same arguments the CLI subcommand would build — no service calls, no duplicated validation (e.g. `edit-token`'s secret-wrapper filter lives once, in `_handle_edit_token`). "Mirror" means no new *behavior* — it does not forbid presentation: item descriptions, install-state labels, and screen order are the TUI's own responsibility as long as they don't call a service or repeat a validation rule that already lives in a `_handle_*`.

## Testing

- **Markers**: `@pytest.mark.unit` / `.integration`. `--strict-markers` in `addopts` turns a typo'd marker into a hard collection error.
- **HOME isolation**: `conftest.py`'s autouse `_isolate_home` fixture sets `HOME=tmp_path` for every test. `Paths.from_home(tmp_path)` is the test seam; production code only ever calls `Paths.default()`.
- Every install/render behavior in `services/wrappers.py` is pinned in `tests/test_wrappers.py`, including two shell-injection regression tests (token and `--model`).
- **`tests/test_keys.py`** — unit tests of `cli/menu.py`'s pure `_translate` key-sequence parser, with a fake `read_more` (no TTY needed). Pins the escape-sequence edge cases that used to be entirely untested (`_read_key_raw` was never exercised end to end — every menu test injects `read_key` and bypasses the parser): a lone Esc must resolve via a non-blocking peek, not block forever; CSI (`\x1b[A`) and SS3 (`\x1bOA`, application cursor mode) both map arrows; a multi-byte sequence like F5 (`\x1b[15~`) is fully consumed, not partially — leftover bytes previously "pressed" spurious menu items; CRLF/LFCR swallows *only its actual pair byte* (on the short `_PAIR_TIMEOUT`, not the 50 ms `_ESC_TIMEOUT`) so Enter neither double-fires nor eats a fast follow-up keypress, and a non-pair byte is pushed back rather than dropped; `\x03` (Ctrl-C) is a *distinct* `"HARD_CANCEL"`, never folded into `q`/Esc's `"CANCEL"`. One test (`test_read_key_raw_pushback_survives_into_the_next_call`) drives the real `_read_key_raw` over an `os.pipe()` with `termios`/`tty` stubbed — the only test that covers the module-level pending-byte slot, which `_translate` alone cannot prove.
- **`tests/test_menu.py`** — unit tests of `select_from_menu`/`press_any_key` with an injected `read_key` (and a `_FakeTTY` stdout stand-in for the ANSI-redraw assertions). Covers `(value, label)` pair rendering, `hint` correctly extending the redraw frame's line count (a silent-drift-prone number — see `frame_lines` in the source), digit/Home/End/PageUp/PageDown navigation, `MenuCancelled.hard` for both the `"HARD_CANCEL"` key and an injected `KeyboardInterrupt`, cursor hide/show (including on an exception path), truncation to a monkeypatched `shutil.get_terminal_size` (and its absence off a TTY), and numbering (`unnumbered` items get `·` not a digit, and `DIGIT_3` still resolves to the correct item when an unnumbered entry sits before it in the list).
- **`tests/test_tui.py`** — the TUI path is exercised through `main(["tui"])` / `main([])`, patching `code_helper.cli.menu.select_from_menu` and `builtins.input` (both looked up at call time inside `cli/tui.py`, so the patch reaches them). Menu choices are returned **by value**, not by rendered label. Because the menu loops, every command test's menu sequence ends in `"quit"` (the loop would otherwise re-prompt once the fake is exhausted); `add` sequences list two picks (wrapper, then `"__default__"` or `"__custom__"`) since the model prompt is no longer a bare `input()`. One test (`test_tui_add_installs_same_as_cli`) installs via TUI and via CLI into two separate `HOME`s and asserts the generated script bodies are byte-identical — the actual proof of the 1-to-1 contract; `test_tui_loops_after_command` runs two commands before `quit` to prove the loop; `test_tui_error_returns_to_menu` patches `resolve_token` to raise and asserts the error is printed and the menu reappears rather than exiting; `test_tui_soft_cancel_in_submenu_returns_to_main_menu` / `test_tui_hard_cancel_exits_from_submenu_depth` pin the Esc-vs-Ctrl-C navigation contract at sub-menu depth; `test_tui_hard_cancel_inside_edit_token_picker_exits_tui` proves a hard cancel from the CLI-shared `_handle_edit_token` code path still reaches the TUI's top-level catch instead of being swallowed into "cancelled, pause, redraw".
- Manual verification of ANSI redraw/hang behavior on a REAL TTY (these tests all inject `read_key`/`select_from_menu` and cannot see terminal-driver-level bugs — the Ctrl-C/`stream.read` issues above were only caught this way): a `pexpect`-driven PTY session works well for this, since it sets up terminal attributes a hand-rolled `pty.fork()` harness easily gets wrong (a source of false-positive hangs during this project's own debugging).
